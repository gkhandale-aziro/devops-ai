# Aziro Ops — v1.0 Release Checklist

The exact list to walk on a VM **before** tagging `v1.0.0`. Each row is a single verifiable step: if any row fails, the tag waits.

Branch under test: `develop` at the commit you intend to tag.
VM: `aziro@vm-sagarpoc` (or equivalent single-host).

---

## How to use this

1. Work top-to-bottom — later sections assume earlier ones passed.
2. For each row, tick `[x]` only after the **Verify** step succeeds literally.
3. If a row fails, stop. Fix on a branch, re-merge, re-pull on the VM, re-start the checklist from the failed row.
4. Copy the output of the **Verify** column into a gist or paste buffer — useful if you need to compare against a future deploy.

## §1 — Install (fresh deploy)

Follow [deploy-guide.md](./deploy-guide.md). These rows mirror its "Verify" boxes.

- [ ] **1.1** Host prerequisites installed (docker, docker-compose-plugin).
      **Verify:** `docker --version && docker compose version` — both print.
- [ ] **1.2** Repo cloned on VM at `~/devops-ai` on `develop` at expected commit.
      **Verify:** `git rev-parse HEAD` matches the commit you're tagging.
- [ ] **1.3** `.env` generated with fresh secrets (not copied from another box).
      **Verify:**
      ```bash
      awk -F= '
        /^(POSTGRES_PASSWORD|AZIRO_SESSION_SECRET|MINIO_ROOT_PASSWORD)=/ {
          v = $2; gsub(/^"|"$/, "", v);
          if (length(v) < 32) { print $1 " is shorter than 32 chars"; bad=1 }
        }
        END { exit bad }
      ' .env
      ```
      Command exits 0 and prints nothing when all three secrets are ≥ 32 chars.
- [ ] **1.4** Bootstrap admin password set (`AZIRO_BOOTSTRAP_ADMIN_PASSWORD`).
      **Verify:** `grep AZIRO_BOOTSTRAP_ADMIN_PASSWORD .env` — present, not empty.
- [ ] **1.5** LLM provider configured (`AI_MODEL` + API key).
      **Verify:** `grep -E "^(AI_MODEL|GEMINI_API_KEY|OPENAI_API_KEY|ANTHROPIC_API_KEY)=" .env`.
- [ ] **1.6** First `docker compose up -d` succeeds; all 6 services healthy.
      **Verify:** `docker compose ps` — aziro, postgres, redis, minio, backup, ofelia all `Up` / `healthy`.
- [ ] **1.7** `/api/v1/readyz` returns 200 with sqlite OK (pre-migration).
      **Verify:** `curl -s localhost:5000/api/v1/readyz | jq` — `"checks.sqlite": "ok"`.

## §2 — SQLite → Postgres migration

Steps 2.1–2.4 run **before** flipping the app's own `AZIRO_DB_URL` in `.env` (that happens in 2.5). That means the migration commands need Postgres explicitly in their per-invocation env — otherwise `scripts.db` / `scripts.migrate_sqlite_to_pg` fall back to SQLite and silently target the wrong database.

Export the target DSN once at the top of this section, then every `docker compose run --rm -e AZIRO_DB_URL=... aziro …` below inherits it:

```bash
export PG_DSN="postgresql+psycopg://aziro:${POSTGRES_PASSWORD}@postgres:5432/aziro"
```

- [ ] **2.1** Alembic head applied on Postgres.
      **Verify:** `docker compose run --rm -e AZIRO_DB_URL="$PG_DSN" aziro python -m scripts.db current` — prints an Alembic revision hash.
- [ ] **2.2** Dry-run migration enumerates tables + row counts.
      **Verify:** `docker compose run --rm -e AZIRO_DB_URL="$PG_DSN" aziro python -m scripts.migrate_sqlite_to_pg --dry-run` — non-zero counts for `events`, `users`, `audit_log`.
- [ ] **2.3** Execute migration completes without errors.
      **Verify:** `docker compose run --rm -e AZIRO_DB_URL="$PG_DSN" aziro python -m scripts.migrate_sqlite_to_pg --execute` — exits 0.
- [ ] **2.4** Row counts match between SQLite and Postgres.
      **Verify:** `docker compose run --rm -e AZIRO_DB_URL="$PG_DSN" aziro python -m scripts.migrate_sqlite_to_pg --verify` — per-table `ok`, ends with `OK: all tables match`. Any `MISMATCH` / `FAIL:` line means STOP.
- [ ] **2.5** `AZIRO_DB_URL` uncommented in `.env`, app restarted.
      **Verify:** `grep ^AZIRO_DB_URL .env` — line present (no `#`); then `docker compose up -d aziro`.
- [ ] **2.6** `/api/v1/readyz` now shows Postgres.
      **Verify:** `curl -s localhost:5000/api/v1/readyz | jq` — `"checks.postgresql": "ok"`.

## §3 — Functional (the core lifecycle)

The 8-state goal: **Detected → Triaging → Diagnosing → Proposing → Approved → Executing → Verified → Resolved.**
In v1.0 this is backed by: SEV triage (L1/L2/L3) + `events.status` (open/acknowledged/resolved) + audit log. The manual "Approved → Executing" is post-v1.0.

- [ ] **3.1** Login with bootstrap admin works.
      **Verify:** Browser → `https://<host>/login` → credentials accepted → lands on `/events`.
- [ ] **3.2** k8s cluster connects; nodes listed.
      **Verify:** `/settings/connections` → add cluster → status flips to "connected"; `/clusters` lists nodes.
- [ ] **3.3** **Detected:** inject a pod failure; event row appears within 10 s.
      **Verify:** `kubectl run bad --image=does-not-exist:latest --restart=Never`; refresh `/events` — row with reason `ImagePullBackOff` appears.
- [ ] **3.4** **Triaging (L1):** SEV3 row classified with reason + node + namespace; no AI call.
      **Verify:** Event detail page → "SEV3" badge, context fields populated, no "AI answer" section.
- [ ] **3.5** **Diagnosing (L2):** trigger SEV2 (e.g. DiskPressure). AI enrichment completes ≤ 20 s.
      **Verify:** Event detail → "SEV2" badge → "AI answer" section populated.
- [ ] **3.6** **Proposing (L3):** trigger SEV1 (NodeNotReady). AI returns a proposed remediation.
      **Verify:** Event detail → "SEV1" badge → "Proposed remediation" section populated.
- [ ] **3.7** **Approved (manual):** click "Acknowledge" on any event.
      **Verify:** `events.status` row updates to `acknowledged`; UI badge changes; audit_log row written.
- [ ] **3.8** **Resolved (manual):** click "Resolve" on the acknowledged event.
      **Verify:** `events.status` → `resolved`; event moves out of "open" filter.
- [ ] **3.9** Verified (snapshot history): open event → "History" tab shows before/after node state.
      **Verify:** History section lists ≥1 snapshot with timestamp.

> Executing (auto-remediation) is **out of scope for v1.0.** The checklist only verifies that Approved + Resolved transitions are recorded correctly — the state the system actually supports.

## §5 — Chaos (graceful degradation)

- [ ] **5.1** `kill-postgres` drill passes.
      **Verify:** `./ops/chaos/kill-postgres.sh` — ends with `drill passed in Ns`, N ≤ 30.
- [ ] **5.2** During PG outage, `/api/v1/healthz` stayed 200 (no k8s restart would have fired).
      **Verify:** The drill's output includes `healthz: 200` at both baseline AND degradation steps.
- [ ] **5.3** During PG outage, `/api/v1/readyz` flipped to 503.
      **Verify:** Drill output includes `readyz: 503` at degradation step.
- [ ] **5.4** After PG restart, `/api/v1/readyz` recovers ≤ 30 s.
      **Verify:** Drill output includes `recovered in Ns`, N ≤ 30.

## §6 — Security

- [ ] **6.1** Rate limiting active on `/login`.
      **Verify:** 11 rapid bad logins → 429 on attempt 11. `for i in {1..11}; do curl -s -o /dev/null -w "%{http_code}\n" -d 'u=x&p=y' localhost:5000/login; done` — last line `429`.
- [ ] **6.2** Session cookie is `HttpOnly; Secure; SameSite=Lax`.
      **Verify:** Browser DevTools → Application → Cookies → inspect session cookie.
- [ ] **6.3** Secrets not present in repo.
      **Verify:** `git grep -E "(POSTGRES_PASSWORD|API_KEY|SESSION_SECRET)=" -- ':!*.md' ':!*.example'` — no results.
- [ ] **6.4** `/api/v1/*` endpoints require auth (unauth → 401).
      **Verify:** `curl -s -o /dev/null -w "%{http_code}" localhost:5000/api/v1/events` — `401`.
- [ ] **6.5** audit_log rows exist for at least: login, event acknowledge, event resolve, setting change.
      **Verify:** `docker compose exec aziro python -c "from store import db; print(db.get_audit_log(limit=20))"` — rows present with those action names.

## §9 — Sign-off

- [ ] **9.1** All rows above are ticked.
- [ ] **9.2** No SEV1/SEV2 events in `/events` left in `open` state (other than test injections you created).
- [ ] **9.3** `docker compose ps` shows all 6 services healthy after the full checklist run.
- [ ] **9.4** `docs/ops/deploy-guide.md`, `docs/ops/slo.md`, `docs/ops/chaos-drills.md`, `docs/ops/backup-restore.md` all resolve (no dead links).
      **Verify:**
      ```bash
      bad=0
      for f in docs/ops/*.md; do
        # Strip fenced code blocks first so the grep in this very checklist
        # doesn't flag itself — the comment above uses ](./...) as literal
        # example text, not a real markdown link.
        awk 'BEGIN{c=0} /^```/{c=1-c; next} !c' "$f" \
          | grep -oE '\]\(\./[^)#]+' \
          | sed 's/^](\.\///' \
          | while read -r link; do
            target="$(dirname "$f")/$link"
            [ -f "$target" ] || { echo "$f: broken link → $link"; bad=1; }
          done
      done
      exit $bad
      ```
      Command exits 0 and prints nothing when all relative links resolve.
- [ ] **9.5** TODO.md "v1.0 exit criteria" all checked.
- [ ] **9.6** Git tag applied: `git tag -a v1.0.0 -m "..."; git push origin v1.0.0`.
- [ ] **9.7** CHANGELOG.md updated with v1.0.0 section.

Once **9.1–9.7** are all ticked, v1.0.0 is out.

## What this checklist deliberately does **not** verify

- Auto-remediation (Execute step) — out of scope for v1.0
- Multi-node Postgres or Redis HA — out of scope
- Helm / k8s-native deploy — out of scope
- OIDC / SSO — out of scope
- Slack / PagerDuty notifications — out of scope
- Web terminal / YAML editor — out of scope

See [deploy-guide.md](./deploy-guide.md) → "What v1.0 does NOT include" for the full list.
